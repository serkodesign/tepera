# Tepera — контекст проєкту для Claude Code

Це перший Android-проєкт розробника-новачка (vibecoding, ~2 год/день). Джерело істини щодо вимог —
`docs/SRS-offline-tracker.md` (повний документ, **v2.8**). Цей файл — стиснута версія для щоденної
роботи; якщо тут і в SRS є розбіжність — SRS головніший, онови цей файл.

## Що це за застосунок
Android-застосунок з двома пов'язаними ідеями:
1. **Структура доби** (раніше — "Online/Offline баланс", перейменовано у v2.2) — ядро продукту:
   показує три нейтральні складові неспаного дня — Online (автоматично, через системний
   UsageStatsManager), "Ти відмітив" (ручні записи по категоріях) і "Решта дня" (все інше,
   ніколи не подається як прогалина) — з Grace Period Buffer-формулою від точки старту дня
   (перше суттєве розблокування, не від півночі) і налаштовуваним орієнтиром. Свідомо НЕ
   протиставлення Online/Offline на одній шкалі (v1.x-v2.1) — пряме протиставлення структурно
   гарантувало відчуття провини (доказова база, SRS розділ 4).
2. **Логування офлайн-активностей за категоріями** (природа, читання, хобі, рух, живе спілкування,
   справи — Сон прибрано з v2.4, "справи" додано в T-8) — ручне, без автотрекінгу в MVP.
3. **Психологічні принципи подачі (SRS v2.5, розділ 4, FR-P.1–P.6)** — обов'язковий рівень для UI й
   текстів: без мотиваційних цитат, порівняння лише з власною історією (не з нормою), число завжди
   з контекстом (не голий %), без traffic-light кольорів, слово "ціль/таргет" замінене на "орієнтир".
4. **Детекція пауз (SRS v2.6, розділ 3.8, FR-D.1–D.11)** — телефон сам пропонує назвати паузи в
   користуванні (≥30 хв) замість покладатись лише на ручний журнал. Реалізовано: детекція й
   позначення пауз, тепловий патерн доби (компактно на Home, повністю на Stats, несе межі дня —
   FR-D.6/D.8 з v2.8), час останнього використання телефону (FR-D.7, v2.8), пріоритизований
   стек до 3 контекстних карток на Home.

Дизайн-філософія: **Trampoline UX** (1-2 тапи, і назад у реальне життя) + **Monastic Style** (без
бейджів, без стріків, без соціального тиску). Аудиторія: дорослі 20-45, втомлені від скролінгу.

- `applicationId`: `com.serkodesign.tepera`
- `minSdkVersion` = 26 (Android 8.0), `targetSdkVersion` = 36 (Android 16 — обов'язково для Google Play з 31.08.2026)
- Мови: українська (основна) + англійська
- MVP безкоштовний, без реклами. **Платежі — лише через RevenueCat (за прямим запитом користувача):**
  добровільна підтримка розробника ("Пригостити кавою") і інфраструктура Tepera Pro (підписки/
  lifetime, поки без гейтингу) — розділ про RevenueCat нижче

## Стек
Kotlin, Jetpack Compose, Room, ViewModel + StateFlow, Vico (графіки), **Jetpack Glance** (домашній
віджет), **WorkManager** (періодичне оновлення віджета), **UsageStatsManager** (Online-час),
Firebase Crashlytics (лише crash-репортинг).

**v2.0: Health Connect / Sleep API ВИДАЛЕНО зі стеку MVP — перенесено на post-MVP.**

## Архітектура
Один Gradle-модуль, Repository-абстракція (ViewModel ніколи не викликає DAO напряму), UUID (String)
первинні ключі, явна стратегія Room-міграцій, без DI-фреймворку (ручний factory pattern), без KMP-
структури (дані вже платформо-нейтральні, формальний multiplatform-модуль — не зараз).

**Room-міграції — підтверджено важливо на практиці, не лише формальна вимога NFR-5.3:** зміна
`AppDatabase.kt` entities БЕЗ bump `version` і `Migration`-об'єкта (`data/local/Migrations.kt`)
падає з `IllegalStateException` при першому запуску на БУДЬ-ЯКОМУ пристрої з уже встановленим
застосунком старої схеми — відтворено на Samsung S23 при `adb install -r` (детально — ROADMAP.md,
"SRS v2.6 rebase"). Застосунок ще не опублікований, але тестові пристрої вже мають реальні
встановлення — це не гіпотетичний сценарій. Bump версії й Migration — щоразу, без винятків.

## Ключові рішення v2.5 (не перепитувати, не переробляти без явного запиту)

- **Структура доби (FR-3.1–3.12, SRS v2.5, розділ 3.3) — переосмислена в v2.2, спрощена в v2.4:**
  `UsageStatsManager` — protected permission, доступ через Налаштування → Спеціальний доступ (не
  runtime-діалог). Три сегменти на одній шкалі: **Online**, кожна категорія з ненульовим часом
  сьогодні (СВОЇМ кольором — не єдиний "Offline"-блок), **"Решта дня"** (нейтральний залишок,
  ніколи не подається як прогалина). Формула: `знаменник = max(180, хвилин_від_точки_старту_дня)`
  (Grace Period Buffer) — **точка старту дня, НЕ північ:** `BalanceRepository.calculateDayStartMillis()`
  шукає перше "суттєве" розблокування (перший `MOVE_TO_FOREGROUND` будь-якого застосунку після
  півночі); розблокування, що СТАРТУЄ всередині ввімкненого вікна сну (T-12, `SleepWindowRepository`,
  розділ "Ключові рішення T-12" нижче) і триває коротше 5 хв, ігнорується як нічна перевірка
  годинника (узгоджено зі стейкхолдером: SRS текст називав поріг 2-3 хв і окрему межу 05:00, тут
  об'єднані в один механізм). **Найраніший початок дня — 05:00 (за прямим запитом користувача,
  `DAY_START_EARLIEST_HOUR` у `BalanceRepository`):** пошук першого розблокування стартує з
  05:00, розблокування раніше (напр. 00:14) початком дня не вважається; до 05:00 "день ще не
  почався". Орієнтир Online-часу — дефолт 180 хв, налаштовується (SettingsStore.targetMinutes,
  назва в UI **"орієнтир"**, НЕ "ціль"/"таргет" — заборонене слово, SRS розділ 4.3). Позначка
  орієнтиру на шкалі — **тиха вертикальна лінія БЕЗ підпису, ніколи не змінює колір при перевищенні**
  (FR-3.10 — жодного traffic-light кодування). **Exclusion List** (`ExcludedAppEntity`) — застосунки,
  виключені з підрахунку. Без доступу — fallback: чіткий заклик надати доступ, офлайн-логування
  лишається повністю робочим.
  **Підрахунок Online-хвилин — через `UsageEvents` (MOVE_TO_FOREGROUND/MOVE_TO_BACKGROUND), НЕ
  через `queryUsageStats(INTERVAL_DAILY, from, to)`:** останній рахує `totalTimeInForeground` для
  цілого бакета статистики, межі якого не гарантовано збігаються з `[from, to]`, тож для часткової
  доби систематично завищував результат (підтверджено користувачем: 159 хв у Tepera проти 47 хв у
  системному Samsung Digital Wellbeing за той самий момент). `BalanceRepository.getOnlineMinutes()`
  тепер парсить сирі події й обрізає точно по межах запиту.
  **Лаунчер і клавіатура виключені з підрахунку за замовчуванням** (поверх ручного
  `ExcludedAppDao`), визначаються динамічно через `PackageManager` (застосунки, що відповідають
  на `CATEGORY_HOME`) і `InputMethodManager` (ввімкнені IME) — не жорстко захардкоджені пакети,
  бо на тестових пристроях різні лаунчери (One UI Home, Microsoft Launcher).
  **Home:** `BalanceCard.kt` → `MyDaySection` — заголовок "Твій день: X" (FR-3.7, росте разом
  з реальним часом, НЕ фіксовані 24 год), багатосегментна шкала + легенда (кольоровий квадрат +
  назва + час, без відсотків самотужки — FR-P.6). Референс — Figma node 2002:170 (файл
  `UyVsim0I8KSwt6qHakkdxp`, "Everyday_Designs"), розділ 4.4 SRS.
  **Stats-екран (тижневий тренд) переведений на точку старту дня** — `StatsViewModel` рахує
  `calculateDayStartMillis(sleepWindows)` для сьогоднішньої (daysAgo == 0) точки, минулі
  завершені доби лишаються на календарних межах зі знаменником 1440 хв; точка на осі X лишається
  прив'язаною до календарного дня, щоб не зсуватись відносно решти тижня.
- **Категорії (FR-2.1, FR-2.2):** 5 дефолтних — Природа, Читання, Хобі/Творчість, Рух/Спорт,
  **Живе спілкування** (`nameKey = "social"`) — + рівно ОДНА користувацька (`isCustom = true`),
  не необмежена кількість. **Обидва числа змінено в T-8 (tepera-dev-spec.md, розділ "Ключові
  рішення T-12" нижче): дефолтних тепер 6 ("Справи" додано), кастомних дозволено до ДВОХ** —
  опис нижче лишається як історія рішення v2.5. **Сон прибрано з дефолтних у v2.4** (без Sleep API вікно сну було
  здогадкою, поданою як факт) — `TeperaApp.onCreate()` архівує `DefaultCategories.LEGACY_SLEEP_ID`
  щозапуску (ідемпотентно, `archive()`, не видалення — FR-2.3), вікно сну лишається лише технічним
  налаштуванням межі старту дня (T-12, `SleepWindowRepository`, розділ нижче), не видимим сегментом.
- **"Видалення" категорії (FR-2.3):** лише архівація (`isHidden = true`), однаково для дефолтних і
  кастомної. Жодного справжнього видалення з UI.
- **Перекриття часу (FR-1.3):** перевірка лише в межах однієї категорії. Різні категорії можуть
  законно перекриватись (напр. аудіокнига під час прогулянки) — без попередження.
- **Тап-таймер на Home:** тап по категорії на Home починає живий таймер (`ActiveTimerStore`,
  DataStore — не Room, це ефемерний runtime-стан сесії, не потребує міграції), повторний тап по
  ТІЙ САМІЙ категорії зупиняє й зберігає запис (`forceOverwrite = true`, без overlap-діалогу —
  це швидка дія, не ручний ввід). **Одночасно йде лише ОДИН таймер (за прямим запитом
  користувача, скасовує попередню можливість таймити кілька категорій):** старт нової категорії
  спершу зупиняє й зберігає таймер, що вже йшов — однаково на Home, віджеті й у "Ні" сповіщення
  (спільна `toggleCategoryTimer()`). Картка активної категорії отримує кольорову
  рамку (без тексту з часом — за запитом користувача прибрано і живий лічильник M:SS на картці,
  і статичний підпис "X хв" під назвою категорії, лишились тільки іконка/рамка як індикатор).
  Хвилина зараховується лише коли вона повністю минула (floor від секунд, не round і не
  примусовий мінімум 1 хв) — тап коротший за хвилину запис не створює взагалі.
- **Архівація категорій — двостороння:** архівація (`isHidden = true`) і повернення з архіву
  (`isHidden = false`, `CategoryRepository.unarchive()`) обидві доступні з UI. Обмеження "рівно
  одна кастомна категорія" (FR-2.2) лишається — unarchive не звільняє й не займає слот, лише
  перемикає видимість.
- **Віджет (FR-4.1–4.3):** Jetpack Glance, адаптивний 4x1/4x2 через `SizeMode.Responsive`.
  **Без live-таймера в реальному часі** (свідоме спрощення відносно початкової ідеї) —
  статичний стан, оновлюється через WorkManager ~раз на 30 хв.
  **Кнопки категорій на віджеті інтерактивні (за запитом):** тап починає/зупиняє той самий
  тап-таймер, що на Home — спільна логіка винесена в `toggleCategoryTimer()`
  (`data/CategoryTimerToggle.kt`), яку викликають і `HomeViewModel`, і `ToggleCategoryTimerAction`
  (Glance `ActionCallback`, замінив `actionStartActivity`). Активний стан — контрастне кільце
  (`GlanceTheme.colors.error`) + "■" замість літери, без цифр часу (це не порушує "без live-
  таймера" — стан статичний, оновлюється по тапу через явний `TeperaWidget().update()`, не
  по секундах). **Відомий Glance-баг і фікс:** `.background()` можна лише УМОВНО ЗАСТОСОВУВАТИ
  (то є модифікатор, то немає) — RemoteViews-діфінг тоді іноді не знімає раніше встановлений
  фон, і кільце "застрягає" на кнопці після зупинки таймера (відтворено на Samsung S23).
  Фікс: `.background()` викликається ЗАВЖДИ, лише колір змінюється (прозорий за замовчуванням).
- **Health Connect / Sleep API:** повністю поза обсягом MVP. `EntrySource` enum лишає значення
  `HEALTH_CONNECT`/`SLEEP_API` для сумісності зі схемою post-MVP, але в MVP не використовуються —
  усе логування, включно з Рух/спорт і Сон, ручне.
- **Графіки:** Vico (не text-only список, не власний Canvas-движок) — це залишається з MVP, на
  відміну від альтернативної чернетки, яка пропонувала прибрати графіки з MVP.
- **Дозволи:** жодних локаційних дозволів. `PACKAGE_USAGE_STATS` — єдиний чутливий дозвіл MVP,
  запитується з чітким поясненням "навіщо" при онбордингу.
- **Навігація — нижній навбар-"таблетка" (Figma-фрейм Everyday_Designs, Фаза 6, замінив
  попередній Home/Стата/Меню-варіант):** 2 вкладки — Home і Статистика — плюс кругла кнопка "+"
  ПО ЦЕНТРУ тієї самої "таблетки" (одноразовий перехід на Add Entry, НЕ вкладка — без
  popUpTo/selected-стану). Категорії — пункт списку в Налаштуваннях (як Exclusion List), а самі
  Налаштування відкриваються іконкою-шестернею на Home (не вкладка навбару, як раніше). Вкладки
  Home/Статистика перемикаються через `popUpTo(startDestination) { saveState = true } +
  launchSingleTop + restoreState` (стандартний Compose Navigation патерн), без back-стрілки.
- **Перемикач мови застосунку:** 3-way перемикач Системна/Українська/English у Налаштуваннях.
  **НЕ `AppCompatDelegate.setApplicationLocales()`** (перша реалізація, `androidx.appcompat`) —
  та бібліотека застосовує збережену мову до ресурсів лише для `AppCompatActivity` (власний
  `attachBaseContext`-хук у `AppCompatDelegateImpl`); `MainActivity` — звичайний
  `ComponentActivity`, тож виклик лише запам'ятовував вибір (`getApplicationLocales()` коректно
  його повертав), а UI не перемикався — підтверджено на Samsung S23 (Android 16): вибір
  "English" позначався, текст лишався українською. Фікс — `util/LocaleStore.kt`: SharedPreferences
  (синхронне читання, потрібне в `attachBaseContext()` до появи Compose/Coroutines) + ручне
  обгортання контексту (`Configuration.setLocale()` + `createConfigurationContext()`) в
  `MainActivity.attachBaseContext()`, і `Activity.recreate()` після зміни вибору. Працює
  однаково на всіх API-рівнях (26+); `androidx.appcompat` прибрано із залежностей.

## Явно поза обсягом MVP
DI-фреймворк, мультимодульність, формальна KMP-структура, CI/CD, повне тест-покриття (лише smoke-
тести), шифрування даних на диску, складні кастомні анімації, мультипрофілі, хмарний бекенд/
синхронізація, геозони, справжній соціальний шар, live-таймер на віджеті, власний background-сервіс
(лише системні API), власний chart-движок, необмежена кастомізація категорій, Health Connect/Sleep API.

Повний список і обґрунтування — розділ 7 SRS v2.7.

**AccessibilityService-ворота (обговорено, свідомо відкладено в post-MVP, не тікет ТЗ):**
користувач питав, чи можна перехопити відкриття застосунку через СПОВІЩЕННЯ (обхід поточних
воріт, T-4/T-5, що ловлять лише тап по закріпленому ярлику). Обговорено два варіанти:
`NotificationListenerService` (перехопити/замінити сповіщення — відкинуто одразу, `PendingIntent`
опаковано, ризик Play-ревізії через Interference/Deceptive Behavior) і `AccessibilityService`
(ловить перехід БУДЬ-ЯКОГО застосунку на передній план, незалежно від шляху відкриття — технічно
закрив би діру повністю). Свідоме рішення НЕ робити другий варіант навіть post-MVP без нового
явного запиту: (1) прямо суперечить чинному принципу "`PACKAGE_USAGE_STATS` — єдиний чутливий
дозвіл MVP" вище; (2) Accessibility API має задокументовану історію масових видалень Google Play
саме для категорії app-blocking (2019, ActionDash/OFFTIME/AppDetox), вимагає окремої Permissions
Declaration Form + відео, і оновлення, що ДОДАЄ такий дозвіл вже ІСНУЮЧОМУ застосунку, отримує
суворішу перевірку (типова ознака шкідливої поведінки в очах Google — "набрати довіру, тоді
додати інвазивний дозвіл"); (3) технічно слабший результат за поточний підхід — з'являється
короткий спалах цільового застосунку ПЕРЕД паузою (зараз користувач його не бачить узагалі);
(4) суперечить філософії продукту (Trampoline UX, "не оцінює") — 100%-те закриття всіх шляхів
обходу ніколи не було метою, наявна діра (тап по оригінальній іконці/сповіщенню) — прийнятне,
вже задокументоване обмеження. Якщо колись реалізовувати — тільки окремим оновленням ПІСЛЯ
встановлення реальної репутації застосунку (справжні відгуки, стаж), не одразу при першому
релізі.

  тонування залежить ЛИШЕ від стану (`WIDGET_ICON_SELECTED` — непрозорий білий,
  `WIDGET_ICON_UNSELECTED` — напівпрозорий білий 50%), колір категорії в іконці більше не
  використовується взагалі (лишається тільки для кольору клітинок сітки доби). Обидва фікси
  перевірені на Samsung S23 — ліві краї збігаються пікселем, усі 5 іконок відповідають Figma,
  невибрані помітно тьмяніші за вибрану.
  **Третій раунд правок — буквальний spec від користувача (точні hex/прозорість), СКАСОВУЄ
  попередній підхід "обидва стани білі, різниця лише в прозорості":** кнопка категорії — рівно
  48×48dp (не діапазон 48-56dp, як раніше); НЕ обрано — тло `#FFFFFF@0.5` ("ефект скла"), символ
  `#FFFFFF@1.0` (сам символ ЗАВЖДИ непрозорий, прозорість дає лише тло); обрано — тло `#FFFFFF@1.0`,
  символ фіксований `#003926` (ОДНАКОВИЙ для всіх категорій, не колір категорії — саме так було
  в оригінальних Figma-асетах, `fill="#003926"` у filled-варіантах book_5/content_cut/
  directions_bike, перша спроба тонувати вибрану іконку `categoryColor()` була помилковим
  припущенням). Перевірено на Samsung S23 живим тапом по кнопці — обраний стан показує зелений
  символ на суцільно білому колі, неактивні — білий символ на напівпрозорому склі.
  **Четвертий раунд — буквальна вимога "get code з іконок у Figma... без змін", повторний
  get_design_context на 9:609 виявив ПОВНІШИЙ компонент, ніж перша вибірка:** Figma насправді дає
  ОКРЕМІ filled-гліфи для ВИБРАНОГО стану Природи й Живого спілкування (camping/groups) — перша
  версія хибно припускала, що для цих двох є лише один гліф і різницю дає тонування; додано
  `ic_widget_nature_selected.xml`/`ic_widget_social_selected.xml` з точним pathData. Той самий
  повний компонент також дав гліф Справ (checklist) — форма ідентична в обох станах Figma
  (відрізняється лише fill-колір самого асета), тож `ic_widget_errands.xml` замінено на точний
  pathData без окремого "_selected" файлу. **Розмір гліфа всередині кнопки виправлено на буквальний
  з Figma** (`widgetIconGlyphSize()`) — 24dp для book/content_cut/directions_bike, 25.5dp для
  camping/groups/checklist — замість підганяння під майже весь розмір кнопки
  (`size - ICON_PADDING - RING_INSET` ≈ 39dp, обидві константи видалено як мертвий код); Figma
  центрує помітно менший гліф із великим полем навколо. Перевірено на Samsung S23.
  **П'ятий раунд — користувач надав власний 1:1 px-скріншот Figma-фрейму 11:647 (343×214,
  математично збігається з 24 паддінг+48 кнопки+24 проміжок+94 сітка+24 паддінг) для порівняння
  з реальним пристроєм — виявив, що відступи/проміжки/розміри скрізь були довільними
  наближеннями, не буквальними Figma-значеннями.** Виправлено: зовнішній паддінг Column
  8dp→24dp (Figma `p-[24px]`); проміжок між рядом кнопок і сіткою 10dp→24dp (Figma
  `gap-[24px]`); кнопки категорій — БУЛИ фіксованим 4dp gap з `Alignment.Start` (клуб зліва,
  порожньо праворуч), ТЕПЕР `Spacer(defaultWeight())` МІЖ кнопками замінює фіксований проміжок —
  той самий ефект, що Figma `justify-between` (Glance Row не має Arrangement.SpaceBetween);
  проміжок клітинок сітки 4dp→10dp (Figma `gap-[10px]`); стеля розміру клітинки 20dp→16dp
  (буквальний Figma `size-[16px]`, розмір лишається адаптивним — 16px×12+10px×11=302px
  перевищує і заявлену ширину контейнера Figma (295px), і реальну доступну ширину віджета на
  вужчих launcher-гридах, фіксація спричинила б обрізання); радіус кутів клітинки — був
  пропорційний 0.35×розмір (довільна апроксимація), тепер точний Figma коефіцієнт 6/16=0.375.
  Перевірено пікселями на Samsung S23 після фіксу: лівий край ряду кнопок і сітки збігається
  (133px проти 131-133px, у межах округлення рендера).
  **Шостий раунд — "Імпортуй всі ці іконки в проект":** повний компонент 9:609 містить 8
  активностей (Reading/Sport/Hobby/Walk/Sleep/Nature/Time with people/Errands), Tepera мала
  готові drawable лише для 6. Додано `ic_widget_sleep.xml`/`ic_widget_sleep_selected.xml`
  (partly_cloudy_night, замінює попередній власноруч намальований "ліжко" — Сон legacy, v2.4,
  але тепер підключений в `widgetIconRes()` і на реальний вибраний гліф, не лише unselected) і
  `ic_widget_walk.xml`/`ic_widget_walk_selected.xml` (footprint, імпортовано для повноти набору,
  СВІДОМО НЕ підключено в `widgetIconRes()` — у Tepera немає окремої категорії "Прогулянка",
  Рух/спорт уже представлений велосипедом). Компіляція й запуск на Samsung S23 без падінь.
  **Сьомий раунд — "онови цю іконку" на node 9:599:** невибраний велосипед (`ic_widget_movement.xml`)
  раніше був видобутий з ФЛЕТТЕНОВАНОГО Figma-асета кнопки (фон-коло + гліф разом, viewport 48x48,
  зсув +12) — цей запит дав чистий окремий `size-[24px]` актив (data-node-id 31:1361), той самий
  формат, що book_5/content_cut. Замінено на нього, viewport 48x48→24x24. Заразом виявлено й
  задокументовано (не баг коду, а особливість тестового середовища): дві незалежні прикріплені
  копії віджета (компактна на сторінці 1, розширена на сторінці 3) НЕ синхронізують RemoteViews
  одна одну — `ToggleCategoryTimerAction.update()` оновлює лише той glanceId, з якого прийшов тап,
  тож стан другої копії лишається візуально застарілим до її власного наступного тапу/оновлення
  WorkManager, хоча дані в DataStore (`active_timers.preferences_pb`) вже коректні одразу.
  Перевірено прямим читанням DataStore через `run-as` + одиничні таповидтики з очікуванням
  ~3-4с між ними на Samsung S23 — новий гліф коректно відповідає стану (контурний на склі,
  зелений на білому колі).

## Тестові пристрої в наявності
Samsung S23 (Android 16), Motorola G84 5G (Android 15), Huawei P9 (Android 8), Sony XZ1 Compact
(Android 9). `UsageStatsManager` доступний з Android 5.0+, сумісний з усіма чотирма без обмежень.

- **Налаштування віджета — вибір і порядок кнопок + віджети 1x1 та 2x1 (за прямим запитом користувача):**
  Налаштування → Активності → "Кнопки віджета" (`WidgetSettingsScreen`). ОДИН спільний впорядкований список
  категорій для всіх розмірів (`SettingsStore.widgetCategoryIds`, DataStore, не Room — міграція не потрібна):
  1x1 бере першу, 2x1 — перші дві, 4x1/4x3 — до 5. Порядок міняється перетягуванням за ручку (власний
  `detectDragGestures`, без бібліотеки), додавання/прибирання — тапом. Порожній список = автоматичне
  сортування за порою доби (FR-4.5, `categoriesForWidget()` у `WidgetLogic.kt`). `TeperaWidget1x1`/`2x1`
  (+ресівери, `SizeMode.Single`, лише кнопки 48dp на тому ж градієнті, `SmallWidgetContent`) — підкласи
  `TeperaWidget` з `maxButtons`. **Перевірено на Samsung S23:** екран, вибір, перетягування, реєстрація
  провайдерів і прев'ю в системі; самі віджети 1x1/2x1 на робочому столі наживо ще не розміщувались.

- **Віджети — новий стиль за Figma "App concept" (nodes 234:442 "Activity icons 2", 234:788 4x1,
  235:935 2x1, 234:808 1x1, 234:848 4x2), СКАСОВУЄ темний градієнтний стиль вище (за прямим
  запитом користувача):** БЕЗ фону віджета — кола 64dp прямо на шпалерах. Невибрана кнопка — біле
  коло + сірий (#505050) контурний гліф; вибрана (запущений таймер) — коло відтінку категорії +
  темний заповнений гліф того ж відтінку (`FIGMA_TINTS` у `TeperaWidget.kt`, значення макета);
  для власних категорій (у макеті нема) — їхній колір із прозорістю 25% і затемнений гліф. Гліфи —
  `ic_widget2_*` 1:1 з SVG макета (не плутати зі старими `ic_widget_*`, які й далі використовують
  Home/AddEntry). Ряд 4x1 — justify-between при 5 кнопках, при меншій кількості щільно з проміжком
  8dp; 2x1 — дві кнопки з проміжком 8dp по центру, 1x1 — одна по центру. Розширений 4x2: ряд + 12dp
  + напівпрозора картка (#FFFFFF@30%, радіус 16, відступ 12) із сіткою 12x4 (проміжок 3dp, радіус
  клітинки 4dp; майбутнє — rgba(167,167,167,.5)). Висота клітинки адаптивна до 23.5dp (макет),
  розмір кола фіксовано 64dp. **Перевірено на Samsung S23** (4x1, 4x2, 2x1, 1x1, вибраний стан);
  Huawei P9/Motorola G84 не перевірялись. Старі drawables (`widget_gradient_bg`, `ic_widget_*`
  тощо) частково більше не використовуються віджетом — не видалені.
  **Уточнення за новим макетом (node 236:956, за запитом користувача):** кнопки зменшено до 56dp і
  всі ряди кнопок (4x1, верхній ряд 4x2, 2x1, 1x1) лежать у напівпрозорій капсулі 72dp заввишки
  (#FFFFFF@30%, радіус 100, відступ 8; 1x1 — коло 72dp). Макета капсули для 2x1/1x1/4x2 нема —
  перенесено з 4x1 за рішенням "усі віджети під цей". Розширений 4x2 = капсула 72 + 12 + картка 127 =
  211dp (`DpSize(250, 211)`). Перевірено на Samsung S23.
