# PostHog (EU): покрокове налаштування — інструкція для власника

Створено 26.11.2026. Назви пунктів меню в PostHog можуть відрізнятися від наведених (інтерфейс змінюється) — звіряти з тим, що
видно в акаунті. Контекст: Фаза 3 аналітики, див. `ANALYTICS-PROGRESS.md` і `docs/privacy-policy-analytics-level2-draft.md`.

## 1. Акаунт і проєкт (EU)
1. **eu.posthog.com** → реєстрація. Регіон **EU Cloud** (Франкфурт). Регіон потім не змінити; у застосунку вже `eu.i.posthog.com`.
2. Створити організацію і проєкт «Tepera». Майстер налаштування можна пропустити. Крім Product analytics, нічого не вмикати.
3. Увімкнути **2FA** (Account settings → Security).

## 2. Приватність (до отримання ключа) — обов'язково, на цьому тримається текст політики
1. **Project settings → General → IP data capture configuration** → увімкнути **Discard client IP data**.
2. **Data pipelines → Transformations** → вимкнути **GeoIP** (застосунок і так шле `$geoip_disable` на кожній події, але в політиці
   сказано «IP не зберігаються» — вимикаємо на обох рівнях).
3. **Session replay** і **Surveys** — вимкнені (застосунок їх не використовує).
4. Автозбір/ефемерні дані — вимкнути, якщо такі перемикачі є (для Android не потрібні).

## 3. Ключ проєкту
1. **Project settings → Project API key** → скопіювати (починається з `phc_`).
2. У `local.properties` на машині, що збирає реліз:
   ```
   posthog.apiKey=phc_ваш_ключ
   ```
   Файл не комітиться. Хост у коді вже `https://eu.i.posthog.com`. **Без цього рядка збірка працює без віддаленої аналітики.**
3. Бажано другий проєкт **«Tepera dev»** з окремим ключем — для власних тестів, щоб не забруднювати бойові метрики. Бойовий
   ключ — лише на момент релізної збірки, ніколи в debug.

## 4. Перевірка, що події доходять (потрібен пристрій з інтернетом — S23/G84; P9 був без мережі)
1. Зібрати й поставити збірку з ключем (dev-проєкту).
2. У застосунку натиснути «Так, допомогти» або ввімкнути перемикач: Налаштування → Дані й приватність → «Допомогти покращити Tepera».
3. Походити вкладками, додати активність.
4. PostHog → **Activity → Live events** (або Events). Затримка до хвилини (SDK шле пачками: 20 подій або за таймером).
5. Мають бути `analytics_consent_changed`, `tab_viewed`, `activity_added`. **Не має бути** подій категорії B
   (`intention_*`, `puzzle_*`, `soft_exit_*`, `risk_window_started`). У властивостях жодних назв/пакетів застосунків.
6. Вимкнути перемикач — нові події перестають приходити.

## 5. Корисні дашборди (після релізу, необов'язково)
- Воронка активації (Insights → Funnel): `onboarding_started` → `onboarding_step_completed` (за `step`) → `onboarding_completed`.
- Утримання (Retention): за `tab_viewed`, повернення на 1/7/30 день.
- Використання функцій: `window_added`, `activity_added`, `gate_paused`, `widget_added`.

## 6. Видалення даних на прохання користувача (з'ясувати ДО публікації політики)
У політиці обіцяно видалення за ID аналітики. Профілів людей немає (`personProfiles = NEVER`), тож стандартного «видалити
людину» для цих ID, схоже, нема. Спосіб видалення подій за `distinct_id` перевірити в актуальній документації PostHog або через
їхню підтримку (EU Cloud). Невідомо, який спосіб зараз доступний.

## 6а. Термін зберігання (ОБОВ'ЯЗКОВО до публікації політики)
Політика тепер обіцяє «не довше 12 місяців». У PostHog (проєкт EU) → Settings → Data retention перевірити/вказати 12 місяців
(на безкоштовному плані термін може бути фіксованим — звірити; якщо менший чи більший за 12 міс., виправити текст політики).
Запит на стирання: лист від користувача містить ID — видалити події за `distinct_id` (спосіб з розділу 6).

## 7. Далі поза PostHog
1. Ключ у `local.properties` (розділ 3).
2. Політика, лістинг, Data safety — за `docs/privacy-policy-analytics-level2-draft.md` (розділи 2–4) — **до** викочування.
3. Версія без суфікса `-beta`, AAB `bundleBetaRelease`, перевірка release (R8) на пристрої. Спершу Open testing.
4. Не збирати debug/тестові збірки з бойовим ключем.
