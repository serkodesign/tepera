## 1. Вступ

### 1.1 Мета документа
Визначити повний обсяг функціональних і нефункціональних вимог до MVP мобільного застосунку — трекера офлайн-активностей і структури доби, — достатній для самостійної розробки одним розробником у форматі vibecoding.

### 1.2 Область застосування
Android-застосунок **Tepera** (`applicationId`: `com.serkodesign.tepera`), перший реліз у Google Play. iOS — окремий проєкт після стабілізації Android MVP.

### 1.3 Візія продукту
Tepera будується на двох принципах дизайну (прийнято з v1.9):

- **Trampoline UX (ефект трампліна):** взаємодія із застосунком — надшвидка (1-2 тапи) фіксація активності, після чого користувач одразу повертається до реального життя. Застосунок свідомо не намагається утримати увагу.
- **Monastic Style (монастирський стиль):** спокійний UI без агресивних бейджів, без push-сповіщень про "стріки", без червоних лічильників і ігрофікованого тиску. Фокус на спокійному усвідомленні балансу, не на змаганні із собою.

Ці принципи узгоджуються з уже прийнятим "без соціального шару, без гейміфікації" (SRS v1.x) і поширюються тепер і на UI-мову віджета та головного екрана.

### 1.4 Визначення та скорочення
- **MVP** — Minimal Viable Product
- **Структура доби** (раніше — "Life Balance", потім "Online/Offline баланс") — подання неспаного дня трьома сегментами: Online, "Ти відмітив", Решта дня (розділ 3.3, оновлено у v2.4 — сон більше не окремий сегмент). Свідомо **не** протиставлення двох величин на одній шкалі
- **Решта дня** — сегмент незалогованого неспаного часу (дорога, готування, розмови). Нейтральна, найбільша частина доби, ніколи не подається як прогалина
- **Grace Period Buffer** — математичний буфер у формулі балансу, що уникає викривлення співвідношення на початку доби
- **Exclusion List** — список застосунків, чий час використання не враховується як "Online"-залежність (напр. навігація, е-книги, банкінг)
- **UsageStatsManager** — системний Android API для читання статистики використання застосунків
- **Vibecoding** — розробка в парі з AI-асистентом

### 1.5 Джерела вимог
Серія уточнювальних сесій зі стейкхолдером + зовнішній чернетковий документ v1.9, узгоджений по пунктах перед злиттям (розділ відповідних рішень нижче).

## 2. Загальний опис

### 2.1 Перспектива продукту
Самостійний offline-first Android-застосунок у ніші slow-living / digital detox. Позиціонування частково зміщується ближче до категорії "трекери екранного часу" через використання даних екранного часу — це усвідомлений компроміс (див. розділ 11, ризик конкурентного позиціонування), компенсований відсутністю блокування (лише візуалізація й усвідомлення, без примусових обмежень) та категорійним трекінгом офлайн-активностей, якого немає в прямих конкурентів.

### 2.2 Функції продукту (короткий огляд)
- Автоматична детекція пауз, меж дня й часових патернів з даних `UsageStatsManager` (розділ 3.8)
- Ручне логування офлайн-активностей за категоріями — доповнює автоматику, не є єдиним способом вводу
- Розрахунок і візуалізація структури доби за трьома сегментами (Grace Period Buffer, налаштовуваний орієнтир, Exclusion List)
- Адаптивний домашній віджет (Jetpack Glance, 4x1 / 4x2) + Quick Settings tile
- Перегляд статистики та історії (Vico-графіки)
- Керування категоріями (архівація, одна користувацька категорія)

### 2.3 Класи користувачів
Дорослі 20-45 років, які відчувають цифрове вигорання і прагнуть бачити баланс між екранним і реальним часом — без блокування, без гейміфікації.

### 2.4 Модель монетизації
MVP — повністю безкоштовний, без реклами та IAP. Монетизація — поза обсягом MVP.

### 2.5 Середовище експлуатації
- Android 8.0 (API 26) — мінімальна підтримувана версія (`minSdkVersion`)
- Android 16 (API 36) — обов'язковий `targetSdkVersion` для Google Play з 31.08.2026
- Мови: українська (основна), англійська — з першого релізу
- **Health Connect / Sleep API — перенесено на post-MVP (v2.0 продукту, не плутати з версією цього документа).** У поточному MVP Рух/Спорт логується вручну як і решта категорій; сон не логується взагалі й не показується як сегмент (розділ 3.3)

### 2.6 Обмеження дизайну та реалізації
- Розробка одним розробником-новачком, vibecoding, ~2 год/день
- UI-стилі слідують уже встановленому робочому стилю (розділ 4.3–4.4); Figma MCP-конектор підключено для подальшого перенесення деталізованого дизайну, коли він знадобиться, але це не блокує розробку
- Без бекенду — offline-first; єдиний виняток — системний Android Auto Backup
- **Один Gradle-модуль**, без KMP-структури в MVP. Хоча v1.9 згадує "KMP-ready" — формальну мультиплатформну структуру не додаємо зараз (конфлікт із рішенням "без мультимодульності" для новачка); дані вже проєктовані платформо-нейтрально (UUID-рядки, прості типи), тож перехід на KMP при старті iOS-фази буде дешевшим, ніж передчасна інфраструктура зараз

### 2.7 Припущення та залежності
- Google Play Console (новий особистий акаунт, ще не створений) вимагає закритого тестування — 12+ тестувальників, 14 безперервних днів опт-ін
- Health Connect і Sleep API — залишаються в архітектурних планах на post-MVP, конкретні NFR/FR щодо них не деталізуються в цьому документі
- Privacy Policy — публікується на GitHub Pages (URL, не PDF)
- **UsageStatsManager вимагає доступу через Налаштування → Спеціальний доступ → Доступ до статистики використання** — не звичайний runtime-діалог дозволу. Застосунок має чітко пояснити цей крок при онбордингу, оскільки без нього ядро функціоналу (сегмент Online у структурі доби) не працює

## 3. Функціональні вимоги

### 3.1 Модуль "Ручне логування активності"

**Змінено у v2.6:** ручне логування лишається повноцінним, але **більше не є головним і єдиним способом вводу** — основну частину структури дня застосунок виводить сам з даних `UsageStatsManager` (розділ 3.8). Ручний ввід потрібен для того, чого телефон не може знати: чим саме була пауза, і для активностей, під час яких телефон використовувався.
| ID | Вимога | Деталізація |
|---|---|---|
| FR-1.1 | Додавання запису | Категорія, тривалість, дата/час початку, опційна нотатка (до 250 символів) |
| FR-1.2 | Способи вводу часу | Пресети (+15/+30/+60/+120 хв), ручний ввід тривалості, інтервальний вибір (початок/кінець) |
| FR-1.3 | Обробка перекриттів часу | Перевірка лише в межах ОДНІЄЇ категорії (FR-1.4 з v1.5) — діалог заміни/скасування. Різні категорії можуть перекриватись без попередження |
| FR-1.4 | Керування записами | Перегляд історії, редагування будь-якого поля, видалення запису (саме запису, не категорії) |
| FR-1.5 | Автоматичний трекінг (Health Connect / Sleep API) | **Перенесено на post-MVP.** У MVP Рух/Спорт логується вручну, як і решта категорій; сон не входить до категорій ручного логування (розділ 3.3) |

### 3.2 Модуль "Категорії"
| ID | Вимога | Деталізація |
|---|---|---|
| FR-2.1 | Дефолтні категорії | 5 категорій: Природа, Читання, Хобі/Творчість, Рух/Спорт, Живе спілкування. **Змінено у v2.4:** Сон прибрано з категорій ручного логування — див. розділ 3.3, чому сон більше не показується як вимірюваний сегмент. Живе спілкування повертається на звільнений слот (компактна назва в тісному UI, напр. на віджеті — "Люди") |
| FR-2.2 | Користувацька категорія | Можливість додати **одну** власну категорію (назва, колір, іконка з набору) — обмежена кількість, на відміну від необмеженої кастомізації в ранніх версіях документа |
| FR-2.3 | "Видалення" категорії | Лише архівація (`isHidden = true`), однаково для дефолтних і користувацької. Жодного справжнього видалення з UI (рішення з v1.5 залишається чинним) |

### 3.3 Модуль "Структура доби" (ядро продукту, переосмислено у v2.4)

**Три сегменти доби**, не чотири — сон прибрано з видимої моделі. Причина: без Sleep API (post-MVP, розділ 10) вікно сну — це здогадка, подана як факт, і показ вигаданої цифри поруч із двома реально виміряними підриває довіру до всіх чисел. Компроміс, який варто розуміти свідомо: без сну як "подушки" число онлайн-часу виглядає різкіше (та сама тривалість — більший відсоток від коротшого дня). Це прийнятно, доки різкіше число не супроводжується оцінкою (розділ 4).

Три сегменти лишаються протиставленням Online вимірюється автоматично й повно, Offline — лише вручну й вибірково; без нейтрального третього сегмента "Решта дня" офлайн завжди "програвав" би, перетворюючи застосунок на машину провини.

| ID | Вимога | Деталізація |
|---|---|---|
| FR-3.1 | Джерело даних Online-часу | Читання через `UsageStatsManager` — сумарний екранний час, за вирахуванням застосунків з Exclusion List |
| FR-3.2 | Межа "початок дня" (раніше — сегмент "Сон") | **Змінено у v2.4:** сон більше не показується як окремий вимірюваний сегмент. Дефолтне вікно 00:00–06:00 лишається лише як технічне налаштування "коли починається твій день", **редаговане користувачем** (нічні зміни, сови). У UI подається як межа дня, не як заявлена тривалість сну |
| FR-3.3 | Сегмент "Ти відмітив" (раніше — "Залоговане офлайн") | Ручні записи по 5 категоріях (FR-2.1). **Формулювання в UI:** "Ти відмітив", не "Залоговане офлайн" — перше звучить як власна дія людини, друге як звіт (розділ 4.3) |

День — величина, що триває, не фіксована абстракція з півночі. **Не плутати з прибраною метрикою FR-D.6:** тут ідеться про довжину неспаного дня як знаменник для шкали трьох сегментів, а не про проміжок між першим і останнім дотиком до телефону |

### 3.8 Модуль "Детекція пауз, межі дня та контекстні картки" (нове у v2.6)

Ключовий зсув продукту: замість "ти ведеш журнал свого життя" — **"телефон уже знає форму твого дня, допоможи назвати кілька шматків"**. Вирішує дві проблеми, виявлені в аналізі ринку: асиметрію зусиль (Online вимірювався автоматично, Offline вимагав ручної праці) і відсутність механізмів утримання після свідомої відмови від стріків/гейміфікації.

**Технічна передумова:** перехід з `queryUsageStats()` на **`queryEvents()`** — агреговані суми не показують проміжків, потрібен потік подій. Це підвищує важливість спайку у фазі 2.

| ID | Вимога | Деталізація |
|---|---|---|
| FR-D.1 | Детекція пауз | Проміжок без активності на передньому плані **тривалістю від 30 хв** у межах неспаного дня вважається паузою-кандидатом. Коротші ігноруються (душ, черга, магазин — шум) |
| FR-D.2 | Чесне обмеження детекції | Пауза ≠ офлайн-активність. Телефон не відрізняє прогулянку від наради, дороги чи роботи за комп'ютером. Детекція **не робить логування повним**, лише легшим там, де воно доречне. Більшість пауз залишиться безіменними — і чесно піде в "Решту дня" |
| FR-D.3 | Вікно опитування | Картка з паузами показується, лише якщо користувач **сам відкрив застосунок** у вікні **22:00–00:00 (паузи сьогоднішнього дня)** або **00:00–10:00 наступного дня (паузи вчорашнього)**. Після 10:00 — не показується. **Жодних push-сповіщень.** Картка явно вказує "сьогодні" чи "вчора", бо це різні набори даних |
| FR-D.4 | Крайовий випадок нічного графіка | **Відоме обмеження:** жорстке вікно 22:00–10:00 не підходить для нічних змін. Якщо налаштоване вікно сну користувача повністю накриває вікно опитування — картка не показується взагалі, паузи лишаються доступними в історії. Переглянути, якщо будуть скарги користувачів |
| FR-D.5 | Позначення паузи | Тап по паузі → вибір категорії з 5 доступних. Позначена пауза стає звичайним записом (`EntrySource.GAP_LABELED`). Непозначені паузи **можна позначити пізніше в історії**, але застосунок про це ніколи не нагадує |
| FR-D.6 | Межі дня — поглинуті хітмепом (**переглянуто у v2.8**) | Окрема метрика "твій день з телефоном" (проміжок від першого до останнього дотику) **прибрана**. Причини: назва бреше — проміжок включає години, коли телефон лежав у кишені, і читається як час використання; число велике, бо день довгий, а важеля для впливу немає — провина без агентності (розділ 4). Межі дня видно **самі собою** на тепловому графіку (FR-D.8), там, де починається й закінчується тепло, без числа й без формулювання |
| FR-D.7 | Час останнього використання телефону | Окрема метрика: **о котрій людина востаннє брала телефон** за добу. Показується **без висновків і коментарів — просто час**. Обґрунтування: вчасно відкласти телефон перед сном — одна з ключових практик цифрового детоксу, і сам факт говорить голосніше за будь-яку пораду. Метрика **вчорашнього** дня (остання сесія відома лише постфактум) |
| FR-D.7a | Межа віднесення пізнього використання | Сесії **до 02:00** належать попередньому дню, після 02:00 — новому. **Не плутати з вікном сну:** вікно сну (за замовчуванням 00:00–06:00) лишається межею для *початку* дня й детекції пауз; 02:00 — виключно межа *віднесення* пізнього використання. Сесія о 01:42 — це ще вчора, о 02:30 — уже сьогодні |
| FR-D.7b | Формулювання | "Востаннє брав телефон о **01:42**", не "останнє вмикання" — технічно ми бачимо останню сесію на передньому плані, а не вмикання екрана, і назва не повинна обіцяти точності, якої немає. Свідоме рішення: пізнє число соромить себе саме, без коментаря — це той самий принцип, що в механізмі "оцінка → реальність" (факт говорить, застосунок мовчить) |
| FR-D.8 | Часовий патерн (несе також межі дня) | Тепловий графік доби, де видно згущення онлайн-часу **і краї дня** (FR-D.6). **Межа, проведена ножем:** показати патерн — факт (людина робить висновок сама); прокоментувати патерн ("спробуй відкладати телефон о 22:00") — порада, **заборонена** (розділ 4) |
| FR-D.9 | Порожній стан патерну | Поки даних менше тижня: "Тут з'явиться патерн, коли назбирається тиждень даних". Формулювання **не має бути закликом користуватися застосунком** ("користуйтесь принаймні тиждень" — з іншої філософії) |
| FR-D.10 | Контекстні картки | Верх головного екрана: **вертикальний стек, максимум 3 картки** одночасно, за пріоритетом актуальності (час доби, наявність нових даних). **Не карусель** — горизонтальна прокрутка запрошує гортати (dwell time проти Trampoline UX) і ховає вміст за першою карткою |
| FR-D.10a | Черга карток за пріоритетом | Слот 1 назавжди за структурою дня ("My day"). Слоти 2–3 не мають фіксованого вмісту — це черга за актуальністю: (1) дозвіл на статистику не наданий — доки не надано; (2) непозначені паузи — лише у вікні FR-D.3; (3) тижнева "оцінка → реальність" (FR-P.1); (4) час останнього використання телефону (FR-D.7); (5) свідчення власної спроможності (FR-P.3) — раз на місяць або коли назбиралося щось справді нове, не щотижня |
| FR-D.10b | Заборона наповнювача | Якщо кандидатів менше трьох — показувати менше карток, **не добивати наповнювачем**. Якщо кандидат один — індикатора-точок немає взагалі. Застосунок не вигадує собі контент, щоб заповнити слоти |
| FR-D.11 | Компактність карток | Картки — одна-дві строки, без ілюстрацій. Три картки не повинні витісняти шкалу структури дня за межі першого екрана: ядро продукту лишається видимим без прокрутки |

## 4. Психологічні принципи подачі (доказова база)

Розділ доданий у v2.2. Визначає, **як** інформація подається — обов'язковий рівень і для UI, що вже реалізується, і для написання всіх текстів інтерфейсу. Порушення цих принципів робить продукт іншим продуктом, навіть за збереження всього функціоналу.

### 4.1 Доказова основа

- **Сором і провина не працюють.** Дослідження iOS ScreenTime показало: функція змінювала поведінку, але викликала стрес, сором і провину, а користувачі **все одно поверталися** до застосунків попри попередження. Провина додає страждання, не зупиняючи поведінку.
- **Змішані категорії провокують самовиправдання.** Дослідження WellScreen (CHI 2026): коли "хороше" й "погане" використання злиті в одну цифру, людина витрачає енергію на внутрішній захист его, а не на усвідомлення. → обґрунтування Exclusion List (FR-3.10).
- **Обмеження викликають реактивність.** Push-фактори, що втручаються в намір користувача, загрожують автономії й ведуть до відторгнення втручання. Примус може бути ефективним рівно доти, доки людина його терпить.
- **Автономія — механізм, що працює довго.** Теорія самодетермінації: стійка зміна залежить від автономії, компетентності й зв'язності. У шкільному дослідженні саме зміни в автономній мотивації опосередкували ефект на екранний час через 18 місяців.
- **Натхнення шкодить, розширення можливостей допомагає.** У дослідженні mHealth-застосунку для відмови від куріння "надихання" користувачів було **негативно** пов'язане з успіхом, тоді як психологічне розширення можливостей (empowerment) — позитивно.
- **Тиха присутність краща за конфронтацію.** У дослідженні переривання скролінгу пряма самоконфронтація (живе відео себе) працювала гірше через збентеження й реактивність, а пасивна відбивна поверхня — найкраще за наміром використання й задоволеністю.

### 4.2 Функціональні вимоги, що випливають

| ID | Вимога | Деталізація |
|---|---|---|
| FR-P.1 | Механізм "оцінка → реальність" | Раз на тиждень (необов'язково, кнопка/жест "Пропустити" завжди видима): "Скільки, на твою думку, ти був онлайн цього тижня?" — **вибір з діапазонів** (напр. "до 10 год" / "10–20 год" / "понад 20"), не відкрите поле вводу — нижчий поріг взаємодії, менше відчуття екзамену. Потім показ реального числа поруч. Рефлексію запускає **власний розрив** людини, а не оцінка застосунку. Найсильніша знахідка з доказової бази |
| FR-P.2 | Онбординг: питання про цінності | Одне питання при першому запуску: "Що ти хотів би робити більше?" (вибір із категорій). Далі статистика подається через призму **власної названої цінності**, а не абстрактної норми |
| FR-P.3 | Свідчення компетентності замість натхнення | Тихі факти власної здатності ("за цей місяць — 14 прогулянок") замість мотиваційних цитат. **Мотиваційні цитати в застосунку заборонені** — доказова база показує негативний зв'язок з успіхом |
| FR-P.4 | Пояснювальні сторінки — "чому ми так", не "чому скролінг шкідливий" | Пояснення, чому застосунок не блокує й не соромить, підсилює автономію. Моралізація про шкоду скролінгу викликає реактивність — заборонена |
| FR-P.5 | Порівняння лише з власною історією | "Довше, ніж твоє середнє за тиждень" — дозволено. "Вище рекомендованого", порівняння з іншими користувачами чи з нормою — заборонено |
| FR-P.6 | Число завжди з контекстом, ніколи відсоток самотньо | "2 год 15 хв з 3 год 20 хв неспання" — факт. "68%" — сприймається як оцінка |

### 4.3 Принципи оформлення UI і текстів

- **Жодного trafic-light кодування.** Червоний/зелений читається як вирок навіть за нейтрального тексту. Палітра тепла, приглушена, не тривожна
- **Аудит усіх текстів на оцінювальні слова.** "Забагато часу онлайн" → "Сьогодні: 3 год 12 хв онлайн". Факт, не оцінка
- **Порожній стан без докору.** Не "Ти нічого не зафіксував", а "Поки порожньо"
- **Уникати слова "ціль"/"таргет" в UI.** "Твій орієнтир" або засічка без підпису — те саме інформаційно, без присмаку невдачі
- **Віджет: шкала тихіша за кнопки логування.** Головна дія віджета — зафіксувати життя, а не подивитись вирок. Число не домінує візуально
- **Сегмент "Решта дня" подається нейтрально-тепло**, ніколи як прогалина в даних

### 4.4 Референсний макет (низька деталізація, робочий орієнтир для UI)

Створено орієнтовний low-fidelity макет головного екрана, віджета 4×2 й картки тижневої рефлексії — демонструє застосування принципів 4.3 на конкретних елементах UI. Це вже встановлений робочий стиль (не тимчасова заглушка) — реалізація в коді слідує йому, поки не з'явиться підстава його змінити.

**Головний екран:**
- Заголовок дня за FR-3.7: "Твій день триває 9 год 40 хв"
- Горизонтальна шкала трьох сегментів (Online / Ти відмітив / Решта дня), приглушені кольори (блакитний, зелений, теплий сірий — не trafic-light), тонка засічка орієнтиру без підпису й без зміни кольору
- Легенда під шкалою: колірний квадрат + назва сегмента + час, без відсотків самотужки (FR-P.6)
- Список сьогоднішніх записів під легендою — іконка категорії, назва, тривалість

**Віджет 4×2:**
- Та сама тришарова шкала, але заввишки ~8px — суттєво тихіша за кнопки під нею
- П'ять круглих кнопок категорій (FR-2.1) в один ряд, іконки Tabler-стилю, компактні підписи (напр. "Люди" замість повного "Живе спілкування" — обмежений простір)

**Картка тижневої рефлексії:** питання + три кнопки-діапазони (FR-P.1) + видимий підпис "Можна пропустити"

**Ключове дизайн-рішення, яке варто зберегти буквально при реалізації:** засічка орієнтиру — це просто тонка вертикальна лінія на нейтральному фоні, без жодної реакції на перевищення. Якщо з'явиться спокуса підсвітити перевищення кольором — це сигнал звірити рішення з розділом 4, не з інтуїцією "так зрозуміліше".

## 6. Нефункціональні вимоги

### 5.1 Продуктивність
Холодний старт до 2с. Читання `UsageStatsManager` — потенційно повільніша операція за прямі Room-запити; виконувати на `Dispatchers.IO`, кешувати результат на час сесії, не запитувати на кожен recomposition.

### 5.2 Безпека та приватність
- Аналітика: лише crash-репортинг (Firebase Crashlytics), без usage-аналітики, без рекламних SDK
- **Оновлено в v2.0:** застосунок читає статистику використання ВСІХ застосунків на пристрої через `UsageStatsManager` — найчутливіші дані в цьому MVP. Дані обробляються й лишаються **виключно локально**, ніколи не передаються на сервер, не логуються в crash-репорти. Це прямо й чесно вказується в Privacy Policy та Data Safety form (FR-7.3)
- Шифрування даних на диску — поза обсягом MVP

### 5.3 Надійність
Явна стратегія Room-міграцій з першої версії БД, без `fallbackToDestructiveMigration()`.

### 5.4 Юзабіліті та доступність
Базовий рівень — системні дефолти Android/Compose semantics, без додаткової доробки на MVP.

### 5.5 Локалізація
Українська та англійська з першого релізу, усі рядки в string resources.

### 5.6 Сумісність
- `minSdkVersion` = 26, `targetSdkVersion` = 36 (обов'язково з 31.08.2026)
- Тестова матриця: Samsung S23 (Android 16), Motorola G84 5G (Android 15), Huawei P9 (Android 8), Sony XZ1 Compact (Android 9)
- `UsageStatsManager` доступний з Android 5.0+, сумісний з мінімальною версією без обмежень (на відміну від Health Connect, який мав нижню межу Android 9)

### 5.7 Архітектурна готовність до розвитку

## 9. Критерії успіху MVP

**Важливе застереження щодо очікувань:** доказова база не дає підстав очікувати значного падіння екранного часу. РКД активних nudge-втручань (n=17, тобто слабкий доказ) не виявило значущого ефекту на сам показник екранного часу. Застосунки цієї категорії дають скромний і часто короткочасний ефект на метрику годин. Побудова очікувань навколо "користувачі зменшать скролінг на 30%" веде до спокуси додати стріки й тиск — що зруйнує саму основу продукту (розділ 4).

### 9.1 Реліз
Успішний публічний реліз у Google Play + перші реальні користувачі (органічні, через Threads-аудиторію).

### 9.2 Продуктова здоровість (перші місяці)
- Люди повертаються логувати через 2–4 тижні (утримання важливіше за встановлення)
- Дозвіл на статистику використання надають — якщо більшість зупиняється на цьому екрані, проблема в поясненні (FR-3.11), а не в продукті
- Люди користуються Exclusion List — ознака, що число почало сприйматись як своє, а не як звинувачення

### 9.3 Головний критерій — якісний, не вимірюваний аналітикою
Оскільки в MVP свідомо немає usage-аналітики (лише crash-репорти, NFR 6.2), основне джерело сигналу — відгуки в Play Store і Threads-аудиторія.

- **Успіх звучить як:** "вперше застосунок про екранний час не змусив мене почуватись погано"
- **Провал звучить як:** "цифри лякають", "відчуваю провину" — **навіть якщо утримання при цьому високе**

### 9.4 Реалістичні очікувані ефекти (у порядку ймовірності)
1. Людина вперше бачить чесне число без внутрішнього спротиву (завдяки Exclusion List)
2. З'являється звичка помічати офлайн-моменти — сам акт логування цінніший за статистику
3. Зміщується не кількість часу, а його усвідомленість
4. У частини людей — поступове зменшення екранного часу, повільне й без драми

## 10. Пост-MVP (довідково)
Health Connect / Sleep API автоматичний трекінг, live-таймер на віджеті, необмежена кастомізація категорій, детальна аналітика й тренди за місяці/роки, розумні інсайти й контекстні підказки, справжній соціальний шар, хмарна синхронізація, iOS-реліз, стріки/цілі, фото до записів, push-нагадування, експорт CSV/PDF, Wear OS, монетизація, **"ворітна" іконка для обраних застосунків (розділ 10.2)**.

### 10.1 iOS-реліз — технічна примітка на майбутнє
Перенесення на iOS реалістичне через **Kotlin Multiplatform (KMP)** — Room (стабільно з 2.8.2), DataStore і Lifecycle/ViewModel уже мають стабільну KMP-підтримку, і наша архітектура (UUID-ключі, Repository-абстракція, платформо-нейтральні data classes) вже готова до цього шляху без переробки.

**Переноситься в спільний `shared`-модуль майже без змін:** Entity-класи, Room-схема й DAO, бізнес-логіка Repository (перевірка перекриття, архівація категорій, формула Grace Period Buffer), DataStore-налаштування.

**Потребує повністю нативного написання, без спільного коду:** UI-шар (SwiftUI або Compose Multiplatform), Jetpack Glance-віджет → WidgetKit, Quick Settings tile (концепції немає на iOS), WorkManager → BGTaskScheduler.

**Критичне архітектурне обмеження — ядро продукту потребує переосмислення, не порту:** `UsageStatsManager` не має прямого еквівалента на iOS. Apple's Screen Time API (Family Controls / DeviceActivity) працює через ізольований App Extension (`DeviceActivityReport`) з токенізованими (privacy-preserving) ідентифікаторами застосунків, і передача підсумкових чисел з extension назад в основний застосунок — нетривіальна, не до кінця усталена в спільноті задача. **Сегмент Online у структурі доби на iOS доведеться проєктувати заново під ці обмеження, а не переносити як є.**

### 10.2 FR-G — "Ворітна" іконка (post-MVP кандидат)

**Статус:** ідея зафіксована, поза обсягом MVP, реалізація не раніше post-MVP.

**Призначення.** Дати користувачу самостійно налаштувати паузу перед відкриттям обраних ним застосунків — без перехоплення системного рівня, без AccessibilityService. Розглядалась і відхилена для MVP альтернатива — перехоплення запуску застосунку через AccessibilityService/overlay (як у конкурента One Sec) — з двох причин: (1) заводить продукт у перенасичену нішу блокувальників із домінуючим гравцем (peer-reviewed дослідження з Max Planck, >100k відгуків); (2) чотири чутливі дозволи одночасно (usage stats, можлива видимість пакетів, overlay, accessibility) різко підвищують ризик відхилення при Google Play review для нового акаунта розробника, і Android 17 Advanced Protection Mode автоматично відкликає AccessibilityService у застосунків, не класифікованих як інструменти доступності.

**User flow:**
1. Користувач у Tepera відкриває розділ "Застосунки з затримкою" (робоча назва)
2. Обирає застосунок(-ки) зі списку встановлених
3. Tepera створює закріплений ярлик (pin shortcut) на домашньому екрані, що замінює візуально оригінальну іконку
4. Користувач сам видаляє чи ховає оригінальну іконку (Tepera не може зробити це за нього — системне обмеження Android)
5. Тап по новому ярлику → екран-оверлей Tepera: повідомлення + прогрес-бар на N секунд (дефолт, наприклад, 5-10) + кнопка "Не зараз"
6. Якщо дочекався — інтент відкриває цільовий застосунок
7. Якщо "Не зараз" — повернення на домашній екран, дія фіксується як подія для власної статистики, без оцінки (розділ 4)

**Технічний підхід:**
- `ShortcutManager.requestPinShortcut()` — доступний з API 25, сумісний із minSdk 26
- `<queries>` у маніфесті з конкретними package name обраних застосунків — **не** `QUERY_ALL_PACKAGES`
- Compose-екран з таймером + `Intent` на цільовий пакет після завершення
- Жодного AccessibilityService, жодного overlay поверх сторонніх застосунків, жодних нових чутливих дозволів понад те, що вже є в MVP

**Явні обмеження (озвучити чесно в UI, не приховувати):**
- Обхід тривіальний — застосунок усе ще доступний через шухляду застосунків, "Нещодавні", пуш-сповіщення
- Це self-nudge інструмент для людини, яка сама хоче собі допомогти, а не блокування
- Оригінальна іконка застосунку лишається на місці, поки користувач сам її не сховає — технічне обмеження Android, не недоробка

**Психологічна відповідність (розділ 4):** автономія (користувач сам обирає застосунки й може відкотити); відсутність оцінки (подія "не зараз" не подається як перемога, "зачекав і зайшов" — не як поразка); на відміну від конкурента, чия задокументована ефективність побудована на дратівливості механізму, наш варіант свідомо без фрустрації як інструменту — залишається відкритим питанням для майбутнього A/B, чи це послаблює ефект.

**Перед реалізацією — обов'язкові кроки:**
1. Спайк: `requestPinShortcut` + запуск через `<queries>` на всіх 4 тестових пристроях, окремо Huawei/EMUI
2. Відповісти на питання "чим ми кращі за One Sec" — якщо відповіді нема, не робити
3. Перевірити реакцію ранніх користувачів MVP (відгуки, Threads) — чи взагалі просять цю функцію

## 11. Ризики
| Ризик | Вплив | Мітигація |
|---|---|---|
| Google Play review/rejection через чутливий дозвіл `PACKAGE_USAGE_STATS` | Високий | Чіткий онбординг-пояснення, детальна Data Safety form, готовність до додаткового review-циклу Google (типово для цього дозволу) |
| Exclusion List (FR-3.5) може потребувати ще й `QUERY_ALL_PACKAGES` через package visibility filtering (Android 11+) — другий чутливий дозвіл посилює ризик review | Середній-Високий | Спайк-тест на початку фази 2 (перевірити реальну поведінку `queryUsageStats()` щодо видимості пакетів), перш ніж проєктувати UI Exclusion List навколо неперевіреного припущення |
| Конкурентне позиціонування зміщується до перенасиченої категорії "screen time trackers" | Середній | Диференціація через категорійний офлайн-трекінг + Monastic-дизайн без блокування — задокументовано, не приховано |
| Користувачі не завершують ручний крок надання Usage Access (типова проблема цього дозволу — низький completion rate) | Середній | Чіткий заклик до дії з поясненням "навіщо" (FR-7.1), fallback — застосунок функціональний і без цього для офлайн-логування |
| Sleep API/Health Connect відсутні в MVP — менше "автоматичної магії" при першому знайомстві | Низький | Свідомий компроміс заради простішого MVP; повертається в post-MVP |
| Детекція пауз читається як стеження ("застосунок помітив, що я не брав телефон") | Середній | Формулювання карток — про час, не про спостереження за людиною; жодних push; ініціатива лише всередині застосунку (FR-D.3) |
| Стек карток перетворює спокійний головний екран на стрічку | Середній | Жорсткий ліміт 3 картки, вертикальний стек замість каруселі, компактна форма (FR-D.10–D.11); при сумніві — прибирати картки, не додавати |
| `queryEvents()` поводиться інакше на різних OEM (особливо EMUI) | Середній-Високий | Розширений спайк у фазі 2 на всіх 4 пристроях; детекція пауз — не критичний шлях, застосунок лишається робочим без неї |
| Втрата upload-ключа підписання застосунку | Високий | Play App Signing налаштовується в фазі 0 |
| Рекрутинг 12 тестувальників на 14 днів | Середній | Threads-аудиторія (~400 підписників, 150-300k переглядів/міс), почати заздалегідь |
