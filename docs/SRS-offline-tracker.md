## 1. Вступ

### 1.1 Мета документа
Визначити повний обсяг функціональних і нефункціональних вимог до MVP мобільного застосунку — трекера офлайн-активностей і балансу Online/Offline часу, — достатній для самостійної розробки одним розробником у форматі vibecoding.

### 1.2 Область застосування
Android-застосунок **Tepera** (`applicationId`: `com.serkodesign.tepera`), перший реліз у Google Play. iOS — окремий проєкт після стабілізації Android MVP.

### 1.3 Візія продукту
Tepera будується на двох принципах дизайну (прийнято з v1.9):

- **Trampoline UX (ефект трампліна):** взаємодія із застосунком — надшвидка (1-2 тапи) фіксація активності, після чого користувач одразу повертається до реального життя. Застосунок свідомо не намагається утримати увагу.
- **Monastic Style (монастирський стиль):** спокійний UI без агресивних бейджів, без push-сповіщень про "стріки", без червоних лічильників і ігрофікованого тиску. Фокус на спокійному усвідомленні балансу, не на змаганні із собою.

Ці принципи узгоджуються з уже прийнятим "без соціального шару, без гейміфікації" (SRS v1.x) і поширюються тепер і на UI-мову віджета та головного екрана.

### 1.4 Визначення та скорочення
- **MVP** — Minimal Viable Product
- **Online/Offline баланс** (раніше — "Life Balance") — співвідношення часу використання екрана (Online) і зафіксованих офлайн-активностей (Offline) за поточну добу, з візуалізацією на віджеті й головному екрані
- **Grace Period Buffer** — математичний буфер у формулі балансу, що уникає викривлення співвідношення на початку доби
- **Exclusion List** — список застосунків, чий час використання не враховується як "Online"-залежність (напр. навігація, е-книги, банкінг)
- **UsageStatsManager** — системний Android API для читання статистики використання застосунків
- **Vibecoding** — розробка в парі з AI-асистентом

### 1.5 Джерела вимог
Серія уточнювальних сесій зі стейкхолдером + зовнішній чернетковий документ v1.9, узгоджений по пунктах перед злиттям (розділ відповідних рішень нижче).

## 2. Загальний опис

### 2.1 Перспектива продукту
Самостійний offline-first Android-застосунок у ніші slow-living / digital detox. Позиціонування частково зміщується ближче до категорії "трекери екранного часу" через ядро Online/Offline балансу — це усвідомлений компроміс (див. розділ 11, ризик конкурентного позиціонування), компенсований відсутністю блокування (лише візуалізація й усвідомлення, без примусових обмежень) та категорійним трекінгом офлайн-активностей, якого немає в прямих конкурентів.

### 2.2 Функції продукту (короткий огляд)
- Логування офлайн-активностей за категоріями (ручне)
- Розрахунок і візуалізація балансу Online/Offline часу за добу (Grace Period Buffer, налаштовуваний таргет, Exclusion List)
- Адаптивний домашній віджет (Jetpack Glance, 4x1 / 4x2) + Quick Settings tile
- Перегляд статистики та історії (Vico-графіки)
- Керування категоріями (архівація, одна користувацька категорія)

### 2.3 Класи користувачів
Дорослі 20-45 років, які відчувають цифрове вигорання і прагнуть бачити баланс між екранним і реальним часом — без блокування, без гейміфікації.

### 2.4 Модель монетизації
MVP — повністю безкоштовний, без реклами та IAP. Монетизація — поза обсягом MVP.

### 2.5 Середовище експлуатації
- Android 8.0 (API 26) — мінімальна підтримувана версія (`minSdkVersion`)
- Android 16 (API 36) — обов'язковий `targetSdkVersion` для Google Play з 31.08.2026
- Мови: українська (основна), англійська — з першого релізу
- **Health Connect / Sleep API — перенесено на post-MVP (v2.0 продукту, не плутати з версією цього документа).** У поточному MVP всі активності логуються вручну, включно з Рух/спорт і Сон

### 2.6 Обмеження дизайну та реалізації
- Розробка одним розробником-новачком, vibecoding, ~2 год/день
- UI-стилі надходять з Figma через MCP-конектор (підключено), інтеграція — коли дизайн готовий
- Без бекенду — offline-first; єдиний виняток — системний Android Auto Backup
- **Один Gradle-модуль**, без KMP-структури в MVP. Хоча v1.9 згадує "KMP-ready" — формальну мультиплатформну структуру не додаємо зараз (конфлікт із рішенням "без мультимодульності" для новачка); дані вже проєктовані платформо-нейтрально (UUID-рядки, прості типи), тож перехід на KMP при старті iOS-фази буде дешевшим, ніж передчасна інфраструктура зараз

### 2.7 Припущення та залежності
- Google Play Console (новий особистий акаунт, ще не створений) вимагає закритого тестування — 12+ тестувальників, 14 безперервних днів опт-ін
- Health Connect і Sleep API — залишаються в архітектурних планах на post-MVP, конкретні NFR/FR щодо них не деталізуються в цьому документі
- Privacy Policy — публікується на GitHub Pages (URL, не PDF)
- **UsageStatsManager вимагає доступу через Налаштування → Спеціальний доступ → Доступ до статистики використання** — не звичайний runtime-діалог дозволу. Застосунок має чітко пояснити цей крок при онбордингу, оскільки без нього ядро функціоналу (Online/Offline баланс) не працює

## 5. Нефункціональні вимоги

### 5.1 Продуктивність
Холодний старт до 2с. Читання `UsageStatsManager` — потенційно повільніша операція за прямі Room-запити; виконувати на `Dispatchers.IO`, кешувати результат на час сесії, не запитувати на кожен recomposition.

### 5.2 Безпека та приватність
- Аналітика: лише crash-репортинг (Firebase Crashlytics), без usage-аналітики, без рекламних SDK
- **Оновлено в v2.0:** застосунок читає статистику використання ВСІХ застосунків на пристрої через `UsageStatsManager` — найчутливіші дані в цьому MVP. Дані обробляються й лишаються **виключно локально**, ніколи не передаються на сервер, не логуються в crash-репорти. Це прямо й чесно вказується в Privacy Policy та Data Safety form (FR-7.3)
- Шифрування даних на диску — поза обсягом MVP

### 5.3 Надійність
Явна стратегія Room-міграцій з першої версії БД, без `fallbackToDestructiveMigration()`.

### 5.4 Юзабіліті та доступність
Базовий рівень — системні дефолти Android/Compose semantics, без додаткової доробки на MVP.

### 5.5 Локалізація
Українська та англійська з першого релізу, усі рядки в string resources.

### 5.6 Сумісність
- `minSdkVersion` = 26, `targetSdkVersion` = 36 (обов'язково з 31.08.2026)
- Тестова матриця: Samsung S23 (Android 16), Motorola G84 5G (Android 15), Huawei P9 (Android 8), Sony XZ1 Compact (Android 9)
- `UsageStatsManager` доступний з Android 5.0+, сумісний з мінімальною версією без обмежень (на відміну від Health Connect, який мав нижню межу Android 9)

### 5.7 Архітектурна готовність до розвитку
| ID | Вимога |
|---|---|
| NFR-7.1 | UUID замість autoincrement Long як первинний ключ |
| NFR-7.2 | Repository-абстракція між UI/ViewModel і Room |

## 8. Критерії успіху MVP
Успішний публічний реліз у Google Play + перші реальні користувачі (органічні, через Threads-аудиторію).

## 9. Пост-MVP (довідково)
Health Connect / Sleep API автоматичний трекінг, live-таймер на віджеті, необмежена кастомізація категорій, детальна аналітика й тренди за місяці/роки, розумні інсайти й контекстні підказки, справжній соціальний шар, хмарна синхронізація, iOS-реліз, стріки/цілі, фото до записів, push-нагадування, експорт CSV/PDF, Wear OS, монетизація.

### 9.1 iOS-реліз — технічна примітка на майбутнє
Перенесення на iOS реалістичне через **Kotlin Multiplatform (KMP)** — Room (стабільно з 2.8.2), DataStore і Lifecycle/ViewModel уже мають стабільну KMP-підтримку, і наша архітектура (UUID-ключі, Repository-абстракція, платформо-нейтральні data classes) вже готова до цього шляху без переробки.

**Переноситься в спільний `shared`-модуль майже без змін:** Entity-класи, Room-схема й DAO, бізнес-логіка Repository (перевірка перекриття, архівація категорій, формула Grace Period Buffer), DataStore-налаштування.

**Потребує повністю нативного написання, без спільного коду:** UI-шар (SwiftUI або Compose Multiplatform), Jetpack Glance-віджет → WidgetKit, Quick Settings tile (концепції немає на iOS), WorkManager → BGTaskScheduler.

**Критичне архітектурне обмеження — ядро продукту потребує переосмислення, не порту:** `UsageStatsManager` не має прямого еквівалента на iOS. Apple's Screen Time API (Family Controls / DeviceActivity) працює через ізольований App Extension (`DeviceActivityReport`) з токенізованими (privacy-preserving) ідентифікаторами застосунків, і передача підсумкових чисел з extension назад в основний застосунок — нетривіальна, не до кінця усталена в спільноті задача. **Online/Offline баланс на iOS доведеться проєктувати заново під ці обмеження, а не переносити як є.**

## 10. Ризики
| Ризик | Вплив | Мітигація |
|---|---|---|
| Google Play review/rejection через чутливий дозвіл `PACKAGE_USAGE_STATS` | Високий | Чіткий онбординг-пояснення, детальна Data Safety form, готовність до додаткового review-циклу Google (типово для цього дозволу) |
| Exclusion List (FR-3.5) може потребувати ще й `QUERY_ALL_PACKAGES` через package visibility filtering (Android 11+) — другий чутливий дозвіл посилює ризик review | Середній-Високий | Спайк-тест на початку фази 2 (перевірити реальну поведінку `queryUsageStats()` щодо видимості пакетів), перш ніж проєктувати UI Exclusion List навколо неперевіреного припущення |
| Конкурентне позиціонування зміщується до перенасиченої категорії "screen time trackers" | Середній | Диференціація через категорійний офлайн-трекінг + Monastic-дизайн без блокування — задокументовано, не приховано |
| Користувачі не завершують ручний крок надання Usage Access (типова проблема цього дозволу — низький completion rate) | Середній | Чіткий заклик до дії з поясненням "навіщо" (FR-7.1), fallback — застосунок функціональний і без цього для офлайн-логування |
| Sleep API/Health Connect відсутні в MVP — менше "автоматичної магії" при першому знайомстві | Низький | Свідомий компроміс заради простішого MVP; повертається в post-MVP |
| Втрата upload-ключа підписання застосунку | Високий | Play App Signing налаштовується в фазі 0 |
| Рекрутинг 12 тестувальників на 14 днів | Середній | Threads-аудиторія (~400 підписників, 150-300k переглядів/міс), почати заздалегідь |
