# Чернетка Permissions Declaration Form (Accessibility API) — для експериментальної гілки

**Статус: чернетка, НЕ надіслана. Нічого тут не означає, що Google погодиться.** Мета — мати
текст готовим ДО того, як вкладати більше роботи в `experiment/accessibility-gates`, щоб оцінити
реальний policy-ризик раніше, а не після.

Контекст — `CLAUDE.md`, розділ "AccessibilityService-ворота" (рішення post-MVP, не для релізу)
і сесія 2026-10-09, де створено цю гілку як бенч.

## 1. Навіщо застосунку потрібен Accessibility API

> Tepera дозволяє людині самостійно додати коротку паузу (3–20 с) перед відкриттям обраних нею
> застосунків — щоб на мить зупинитись і вирішити свідомо, а не за звичкою. Це core-функція
> застосунку ("Застосунки з затримкою"), яку людина вмикає сама, для обраних нею самою
> застосунків. Accessibility API — єдиний спосіб визначити момент переходу застосунку на
> передній план НЕЗАЛЕЖНО від того, як його відкрили (іконка на робочому столі, список недавніх
> застосунків, сповіщення, голосовий асистент) — без нього пауза спрацьовує лише при тапі по
> окремому закріпленому ярлику, що людина легко обходить, відкривши застосунок звичним шляхом.

## 2. Що саме сервіс робить і НЕ робить

- Слухає **лише** `TYPE_WINDOW_STATE_CHANGED` (перехід на новий екран/застосунок).
- Читає **лише** `event.packageName` — назву застосунку, що виходить на передній план.
- `canRetrieveWindowContent="false"` у конфігу — сервіс **не може** і не намагається прочитати
  текст, зображення чи будь-який вміст екрана жодного застосунку.
- Нічого не записує й нікуди не надсилає — звіряє назву пакета з локальним списком, який людина
  сама склала в застосунку, і за збігом показує власний екран паузи Tepera.
- Чому не альтернатива без Accessibility: `UsageStatsManager` (уже використовується в Tepera для
  решти функцій) дає статистику з затримкою й не гарантує подію "саме зараз, до того як
  застосунок намалював перший кадр" — пауза ПІСЛЯ того, як людина вже побачила застосунок,
  не виконує задуму функції.

## 3. Чому не ширший дозвіл / не інший API

- `QUERY_ALL_PACKAGES` і `canRetrieveWindowContent="true"` свідомо НЕ запитуються — функції не
  потребують ширшого доступу, ніж `event.packageName`.
- `NotificationListenerService` розглядали й відхилили (обговорення в CLAUDE.md) — вищий ризик
  (Interference/Deceptive Behavior policy) і не покриває шлях "тап по іконці на робочому столі".

## 4. Хто бачить цей дозвіл і коли

- Запит НЕ на онбордингу й НЕ автоматично. Дозвіл стає обов'язковим лише в момент, коли людина
  в Налаштуваннях → "Застосунки з затримкою" **сама** перемикає спосіб перехоплення на
  "Accessibility (експериментально)" — явний, добровільний крок на екрані, де вона вже
  налаштовує саму цю функцію.
- Онбординг лише згадує текстом, що ця можливість існує (без діалогу, без запиту дозволу).

## 5. Демо-відео (чернетка сценарію, ≤ 90 с для форми)

1. Налаштування → "Застосунки з затримкою" → додати застосунок X, поставити затримку 10 с.
2. Перемкнути "Спосіб перехоплення" на Accessibility → системний діалог підтвердження →
   Налаштування → Спеціальні можливості → увімкнути Tepera → повернутись у застосунок.
3. Закрити Tepera повністю. Відкрити застосунок X **напряму з робочого столу** (не через ярлик
   Tepera) → показати, що з'являється пауза Tepera, а не застосунок X одразу.
4. Показати той самий результат через "Недавні застосунки" (не лише іконку) — довести, що
   перехоплення не прив'язане до одного шляху відкриття.

## 6. Відкриті питання, які документ (CLAUDE.md) уже позначив як ризики

- Google за останні роки систематично відмовляє "screen time / app blocker" застосункам у
  використанні Accessibility API — ця форма НЕ гарантує погодження, лише формалізує заявку.
- Оновлення, що додає цей дозвіл до **вже опублікованого** застосунку (Tepera в закритому
  тесті), проходить суворішу перевірку, ніж новий застосунок із самого початку.
- Якщо Google відмовить — відкотити до чистого shortcut-механізму (вже є, не видалявся) без
  втрати функціональності для користувачів, які НЕ перемикали режим.

## 7. Рекомендація

Не подавати цю форму, доки:
1. Бенч на тестових пристроях (S23, G84, P9, XZ1) не підтвердив, що детекція реально надійна
   (особливо на P9/EMUI, де фонові служби агресивно вбиваються).
2. Власник не прочитав актуальну Google Play Accessibility API policy (вона змінювалась кілька
   разів за останні роки) і не прийняв усвідомлене рішення про ризик для акаунта розробника.
