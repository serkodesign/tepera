## 2. Online за календарну добу — чи є одна перевикористовна функція

**Так.** `data/repository/BalanceRepository.kt:130` — `getOnlineMinutes(from: Long, to: Long): Int`
парсить сирі `UsageEvents` і обрізає точно по межах `[from, to]` (а не бакети `queryUsageStats`, які
завищують — задокументована пастка, розділ 4 `DECISIONS-Tepera.md`). Для календарної доби D виклик
тривіальний: `getOnlineMinutes(midnight(D), midnight(D) + MS_PER_DAY)`.

Уже перевикористовується в 6 місцях, не продубльована:
- `ui/home/BalanceViewModel.kt:153` — сьогодні (Home).
- `ui/stats/StatsViewModel.kt:204,206,273,276` — "Вчора", тренд тижня, порівняння з попереднім тижнем.
- `data/repository/WelcomeBackRepository.kt:43` — середнє за перерву (CC-4).
- `ui/home/OnlineEstimateRevealViewModel.kt:66` — картка "оцінка → реальність" (T-3).
- `ui/home/WeeklyReflectionViewModel.kt:71` — тижнева рефлексія.

Для почасового розрізу (не одне число на добу, а бакети) є другий, окремий перевикористовний шар:
`getOnlineMinutesPerSlot(fromMillis, slotMinutes, slotCount)` (`BalanceRepository.kt:286`) — на ньому вже
побудовані `PatternRepository.hourlyOnlineMinutes()` і `widget/WeekSnapshotRepository.kt:22` (годинні
бакети для тижневого знімка віджета, W-1/D-33 — наживо з `UsageStatsManager`, без фонових знімків).

**Висновок для P-2:** нова функція "Online за добу D" не потрібна — `getOnlineMinutes(midnight, midnight+24h)`
і так є єдиним джерелом істини для всіх наявних екранів. `day_summaries` лише зберігатиме РЕЗУЛЬТАТ цього
самого виклику для діб, старших за глибину `UsageStatsManager`, — тим самим кодом, тож числа не розійдуться.

## 4. Гілка `feature/monetization-revenuecat`

**Склад:** 0 власних комітів. `git log main..feature/monetization-revenuecat` — порожньо: HEAD гілки
(`b2fa1f8`) — це просто предок `main`, комміт ПЕРЕД `c42e2bf` (CH-01, "remove the payment layer from the
1.0 release", 21.09.2026). Тобто це не фіча-гілка з окремими RevenueCat-коммітами поверх спільної історії,
а "знімок" головної гілки на момент, коли платіжний шар ще не видалили.

**Відставання:** 14 комітів позаду `main`, **80 комітів / 263 файли (+16879/-4693 рядків) позаду
поточної `ui-redesign`** (весь редизайн Figma, темна тема, T-1…T-16, W-1/W-2 — усе це сталося ПІСЛЯ
точки, де стоїть revenuecat-гілка).

**Тест "чи збирається після rebase":** буквальний `git rebase` безглуздий (0 унікальних комітів — нічого
реплеїти). Реальний тест — чи чисто реінтегрується платіжний КОД: у disposable worktree (`git worktree
add`, видалено після тесту) виконано `git revert --no-commit c42e2bf` (тобто "поверни те, що CH-01
видалив") на вершині поточної `ui-redesign`. Результат:

- **Чисто, автоматично:** `app/build.gradle.kts` (залежності `purchases-kmp-*`), `MainActivity.kt`,
  обидва `strings.xml` (UA/EN).
- **Конфлікт, 3 файли, 5 хunk-ів:** `TeperaApp.kt` (2), `ui/navigation/TeperaNavHost.kt` (2),
  `ui/settings/SettingsScreen.kt` (1) — очікувано: саме ці файли й редизайн торкались найбільше
  (нові Repository в `TeperaApp`, нові маршрути в навігації, новий стиль рядків Налаштувань).

**Висновок:** попри вражаючу цифру 263 файли різниці, фактична вартість реінтеграції мала — ядро
redesign (UI-компоненти, палітра, віджети, ворота) і платіжний шар майже не перетинались. Реінтеграція
при відкритті етапу 2 — кілька годин ручного злиття 3 файлів, не переписування з нуля. Worktree і
тимчасові гілки видалені, у `feature/monetization-revenuecat` і будь-де в репозиторії слідів тесту нема.

## 5. RevenueCat проти прямого Play Billing Library

| | RevenueCat (`purchases-kmp-core`+`-ui` 3.9.0, вже був інтегрований) | Play Billing Library (`com.android.billingclient:billing-ktx`, пряма) |
|---|---|---|
| Розмір/складність | KMP-бандл, більший за єдину офіційну бібліотеку; вже був підключений без KMP-реструктуризації проєкту (`docs/revenuecat-setup.md` в архівній гілці) | Менша, офіційна, Google-first; документація й приклади для чистого Kotlin/Android без KMP-шару |
| Офлайн-кеш права | Вбудований (`CustomerInfo`, кешується SDK) | Треба реалізувати самому (кеш останньої успішної перевірки `queryPurchasesAsync`) |
| Відновлення покупки | Вбудоване (`restorePurchases()`) | Треба реалізувати самому (`queryPurchasesAsync` + звірка з entitlement) |
| Acknowledge покупки | SDK робить сам | Обов'язково власноруч (`acknowledgePurchase`), інакше Google повертає кошти автоматично через 3 доби — пряма вимога P-20 плану |
| `PENDING`-стан | Обробляється SDK | Власноруч (слухати `PurchasesUpdatedListener`, стан `PENDING`) |
| Готовий Paywall/Customer Center UI | Так (`purchases-kmp-ui`), уже був підключений і перевірений на Test Store | Нема — екран Pro пишеться самостійно (план P-21 це й так вимагає власного екрана, тож ця перевага RevenueCat частково нівелюється) |
| Майбутня підписка (етап 3) + потенційний iOS | Готово з коробки, та сама абстракція | Підписки — так само Billing Library, але iOS — зовсім інший код (StoreKit), нічого спільного |
| Потік даних про покупку | Через сервери RevenueCat (третя сторона бачить факт покупки/entitlement) → рядок у Data Safety "дані про покупки передаються третій стороні" | Напряму між застосунком, пристроєм і Google — жодної третьої сторони в потоці покупки |
| Вартість сервісу | Безкоштовний tier RevenueCat вистачає з запасом для обсягу Tepera | Безкоштовно (офіційна бібліотека) |
| Вже перевірено | Test Store на S23, конфігурація, offerings, тестова покупка (ROADMAP.md:40) — **реальна оплата й release-ключ `goog_` НЕ перевірялись ніколи** | Взагалі не інтегровано, усе з нуля |

**Рекомендація: лишити RevenueCat (реінтегрувати з архівної гілки), не переходити на пряму Billing
Library.** Причини:
1. Розділ 4 цього аудиту показав, що реінтеграція дешева (3 файли, 5 конфліктів) — головний
   контраргумент "воно застаріло й не зійдеться" не підтвердився.
2. P-20 плану буквально перелічує acknowledge/restore/офлайн-кеш/`PENDING` як обов'язкові пункти — це
   рівно те, що RevenueCat уже вирішує, а розробник-новачок (CLAUDE.md, профіль користувача) ризикує
   реалізувати з помилками наживо на реальних грошах користувачів.
3. Єдиний продукт `tepera_pro` (неспоживний, разова покупка) — найпростіший можливий кейс для RevenueCat,
   без KMP-складності (Paywall/Customer Center тут не обов'язкові до використання, план P-21 і так хоче
   власний екран без зайвих RevenueCat-елементів).
4. Мінус (дані йдуть через стороннього процесора) — реальний, але вже один раз розкритий і прийнятий
   власником при першій інтеграції (Test Store, ROADMAP.md:40); не новий ризик, лише повернення
   задокументованого.

**Контраргумент, який власник має зважити:** якщо колись захочеться повністю нульова залежність від
зовнішніх сервісів у потоці покупки (принцип "нічого не виходить із пристрою", Ж-3 — хоча Ж-3 прямо
каже "жодних власних мережевих запитів", а не забороняє SDK, що сам ними користується) — пряма Billing
Library це дає. Але це суперечить уже прийнятому рішенню при першій інтеграції RevenueCat, тож не
бачу підстави переглядати його саме зараз без нової причини.
