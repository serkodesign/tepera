# ROADMAP — Tepera (SRS v3.1, оновлено 21.09.2026)

Розбивка фаз із SRS v2.0 (розділ 7) на конкретні задачі, Фази 0-6 нижче ще написані до
переосмислення ядра в SRS v2.2-v2.5 (лишені як історія — самі задачі виконані, лише термінологія
застаріла: "Online/Offline баланс" → "Структура доби", "Сон" був серед дефолтних категорій).
Актуальний стан ядра — розділи "SRS v2.5 rebase" … "SRS v2.8 rebase", тікети "T-*" з
`tepera-dev-spec.md`, сесії за прямими запитами й розділи "Сесії 19.09.2026" та "Сесія 21.09.2026"
нижче. **Актуальний SRS — v3.1** (`docs/SRS-offline-tracker.md`, синхронізовано з реалізацією
21.09.2026); `tepera-dev-spec.md` головніший за SRS при розбіжності.
Працювати по одній фазі за раз. Позначай `[x]` по завершенню.

## Фаза 2 — Online/Offline баланс (~3 тижні)
*(нова фаза замість Health Connect/Sleep API з v1.5)*
- [x] **Спайк:** перевірено на реальному пристрої (Samsung S23, Android 16). `queryUsageStats()`
      справді повертає імена пакетів незалежно від package visibility filtering (окремий
      AppOps-грант, не PackageManager query), але резолвити людську назву/іконку через
      `getApplicationInfo()` без додаткової видимості НЕ вдалося — 226 із 580 пакетів, побачених
      за 30 днів, кидали `NameNotFoundException`, включно з реальним застосунком (Pocket Casts).
      Друга проблема: без фільтрації "580 пакетів" — це здебільшого системний шум
      (drivers/RRO-оверлеї), не реальні застосунки. **Рішення без QUERY_ALL_PACKAGES:**
      `<queries>` з intent-фільтром MAIN/LAUNCHER у маніфесті — не вважається чутливим дозволом
      при Google Play review (на відміну від QUERY_ALL_PACKAGES), відсікає системний шум і
      повертає видимість усіх launchable застосунків. Після фіксу: 113 релевантних застосунків,
      0 unresolved. Exclusion List будується саме так.
- [x] Онбординг-екран з поясненням, навіщо потрібен доступ до статистики використання —
      показується автоматично один раз (DataStore-прапорець), перевірено вживу
- [x] Інтеграція UsageStatsManager, читання Online-часу за добу — перевірено вживу з реальними
      даними після надання доступу
- [x] Grace Period Buffer формула, скидання о 00:00 — перенесено з Фази 0 (BalanceRepository),
      маркер таргету на шкалі відображається коректно
- [x] Налаштування таргету (дефолт 180 хв) — SettingsStore (DataStore), екран Налаштувань
- [x] Exclusion List — вибір застосунків зі списку встановлених — перевірено вживу (Карти,
      увімкнення/вимкнення перемикача переживає перезапуск)
- [x] Fallback UI без наданого дозволу — картка балансу на Home показує заклик до дії, поки
      доступ не надано; офлайн-логування (Фаза 1) увесь час лишається робочим
- [x] **Крашфікс:** `queryUsageStats()` кидає `SecurityException` (не повертає порожній список,
      як припускав коментар у коді), якщо доступ був наданий, а тоді вимкнений вручну в
      Налаштуваннях — застосунок падав замість показу fallback. Відтворено на реальному
      пристрої через `adb shell appops set ... android:get_usage_stats deny`; `hasUsageAccess()`
      і `getOnlineMinutes()` у `BalanceRepository` тепер ловлять `SecurityException`
- [x] **UI-покращення (за запитом):** картка балансу — два окремі підписані пропорційні бари
      (Online/Offline зі своїми хвилинами), а не одна шкала без явного відображення Offline;
      маркер таргету лишився на Online-барі. Перевірено вживу
- [x] **Багфікс (за запитом):** `getOnlineMinutes()` через `queryUsageStats(INTERVAL_DAILY, ...)`
      завищував Online-час (159 хв у Tepera проти 47 хв у системному Samsung Digital Wellbeing за
      той самий момент) — межі бакетів статистики не обрізані рівно по `[from, to]`. Замінено на
      підрахунок по сирих подіях `UsageEvents` (MOVE_TO_FOREGROUND/MOVE_TO_BACKGROUND), обрізаних
      точно по запитаному інтервалу — той самий підхід, що й системні лічильники екранного часу.
- [x] **UI-покращення (за запитом):** картка балансу на Home перероблена під стиль віджета — один
      сумісний бар (Online-частка + Offline-частка на одній лінії) з відсотками над ним
      ("Online: 43% · Offline: 57%") замість двох окремих шкал.
- [x] **Багфікс (за запитом):** лаунчер і клавіатура виключені з підрахунку Online-хвилин за
      замовчуванням, поверх ручного Exclusion List — визначаються динамічно через
      `PackageManager`/`InputMethodManager`, не захардкоджені пакети. Перевірено вживу на
      Samsung S23: 67 хв → 59 хв за той самий момент після виключення.

Сьомий тікет робочого ТЗ. Закриває SRS розділ 12, відкрите питання №5: "чи заслуговують 5 кнопок

- [x] **4x2 — рядки поміняно місцями:** структура доби із засічкою орієнтиру тепер ВЕРХНІЙ ряд,

      буквальна вимога документа "4×1 лишається як є". Це також узгоджує код із ОРИГІНАЛЬНИМ

      зверху) — T-7 не вигадує нову композицію, а повертає узгодженість із задокументованим
      макетом.
- [x] **Шкала стала вищою — "читається з відстані витягнутої руки" (документ):**
      `BALANCE_BAR_HEIGHT` 8dp→20dp (2.5×). Кольори/відсутність тексту-підписів не змінились —

      вимога.** `CategoryButtonsRow`'s `coerceIn()` раніше мав нижню межу `1.dp` (лише стеля

      як явна нижня межа `coerceIn()`.

      awful") — маркер орієнтиру рендерився як суцільний ЧОРНИЙ БЛОК, не тиха лінія.**

      довільний `Float` (лише рівний розподіл, на відміну від Compose `Modifier.weight()`) —
      перша спроба (вагові розпірки) не скомпілювалась, тому позиціювання через фіксовану
      ширину. **Перевірено повторним скріншотом на тому самому пристрої** — чорний блок зник,
      лишилась тонка лінія, кольори сегментів під колишньою позицією маркера тепер видно.
- [x] **Перевірка на Samsung S23:** `./gradlew assembleDebug` — успішно, `adb install -r` без
      падіння. Реальний віджет на лаунчері користувача (не тестовий пристрій) підтвердив: рядки

- **Свідомо поза обсягом цієї сесії:** точні значення `BALANCE_BAR_HEIGHT`/`MIN_BUTTON_SIZE` —

## П'ять виправлень і доробок за прямим запитом користувача (не з tepera-dev-spec.md)

- [x] **Ворота: "Не зараз" повертає на робочий стіл, не на внутрішній екран Tepera.** Раніше

      відкрились, поки застосунок уже стояв на ІНШОМУ екрані (напр. `GatesScreen`), один крок
      назад повертав саме туди, а не на робочий стіл, як мало б бути для "тонкого шлюзу".

      `(context as? Activity)?.moveTaskToBack(true)` — застосунок іде у фон, користувач бачить
      лаунчер, а не Tepera. Застосовується однаково для "Не зараз" і для автозапуску таймером —
      обидва шляхи ведуть через `state.finished`.
- [x] **Ворота: видалення ярлика з робочого столу видаляє рядок і зі списку в застосунку.**
      Android не дає колбек на видалення pinned shortcut (спільний для всіх лаунчерів API

  + `bmgr enable false` перед uninstall/install. **Це саме по собі не баг застосунку** (Auto
  Backup — очікувана системна поведінка), але варто тримати в голові як реальний сценарій:
  користувач, що перевстановлює Tepera (новий пристрій, звільнення місця), матиме онбординг-
  прапорці відновленими, а `hasUsageAccess` — ні (рахується наживо з `UsageStatsManager`, не з
  DataStore) — розбіжність нешкідлива тут, бо `HomeScreen` гейтить показ картки доступу саме на
  живий стан, не на прапорець.
  **Реальний регрес, знайдений і виправлений ПІСЛЯ забезпечення справді чистого стану:**
  екран пояснення дозволу (`OnboardingScreen`, T-3, той самий, що отримав новий `onLearnMore` у
  попередній сесії) стабільно пропускався на свіжому встановленні — застосунок стрибав прямо з
  онбординг-оцінки Online-часу на `WidgetSuggestionScreen`, попри те що `onboarding_usage_access_seen`
  фактично виставлявся в `true` (підтверджено прямим hex-дампом DataStore-протобафу). Причина —
  ТОЙ САМИЙ клас гонитви, що вже описаний і частково пофіксований для `POST_NOTIFICATIONS`
  (коментар у `HomeScreen.kt` вище): `OnboardingScreen.kt` виставляє `onboardingUsageAccessSeen`
  у власному `LaunchedEffect(Unit)` ОДРАЗУ при монтуванні, не чекаючи дії користувача; Home
  встигає прочитати це на короткому "оживанні" між `popBackStack()`/`navigate()` і одразу
  штовхає на `WidgetSuggestionScreen`, перш ніж `OnboardingScreen` реально лишається на екрані.
  Це саме той LaunchedEffect (widgetSuggestion-тригер, `HomeScreen.kt`), для якого раніше
  застосували `delay(1000)`-фікс на ІНШОМУ переході (перед POST_NOTIFICATIONS) — цей конкретний
  перехід (permission-екран → widget suggestion) лишався незахищеним. Фікс — той самий
  `delay(1000)` перед `onShowWidgetSuggestion()`, дзеркально до вже наявного патерну.
  **Перевірено наскрізно на Samsung S23, до і після фіксу:** до фіксу — permission-екран жодного
  разу не з'явився за 5 повторних чистих прогонів; після фіксу — з'являється стабільно,
  включно з новим `onLearnMore` (тап відкриває "Базу знань", системна "назад" коректно повертає
  на той самий permission-екран, не далі), скасовує "onLearnMore не перевірено наживо" з
  попередньої сесії.
  **UX-знахідки поза кодовим багом, зафіксовані для майбутньої сесії полірування (не виправлені
  цією сесією — виходить за межі запиту "перевір і дай оцінку"):**
  1. Екрани "Що ти хотів би робити більше?" (values) і "Скільки, по-твоєму, ти був онлайн
     учора?" (T-3 estimate) використовують `verticalArrangement = Arrangement.Center` у
     повноекранній `Column` — з коротким контентом (заголовок + 2-3 рядки) це лишає велику
     порожню зону зверху й знизу, особливо помітно на високих екранах. Екран категорій (T-8,
     6 рядків + кнопка) природно заповнює екран і виглядає інакше композиційно — три "прості"
     екрани онбордингу поспіль мають нерівну візуальну щільність.
  2. Кнопка "Відкрити налаштування" на fallback-картці доступу (Home, `BalanceCard.kt`) реально
     переноситься в 3 рядки з "осиротілим" останнім символом ("Відкрити / налаштуванн / я") —
     `Row` з `TextButton` ("Чому це потрібно?") і `Button` без `weight()`/`fillMaxWidth()` не
     лишає кнопці досить горизонтального місця. Це перший екран, який реально бачить новий
     користувач одразу після онбордингу (якщо дозвіл не надано) — вартий окремого фіксу.
  3. Повний ланцюжок онбордингу — 5 повноекранних кроків (цінності → категорії → оцінка →
     пояснення дозволу → пропозиція віджета) плюс до двох системних діалогів (Налаштування
     Android, потім POST_NOTIFICATIONS) — суттєво довший за "1-2 тапи" Trampoline UX, який
     стосується щоденного використання, не самого онбордингу; сам по собі не проблема (одноразово),
     але жодна з проміжних сторінок не показує прогрес ("крок 2 з 5") — користувач не знає,
     скільки ще лишилось, поки не дійде до кінця.
  Скріншоти всього проходу (values → categories → estimate → permission → learn-more → back →
  widget-suggestion → Home з системним діалогом сповіщень → чистий Home) збережені локально в
  сесії, не в репозиторії (тимчасові, для аналізу).
